## 入口别名与独立创建

bridge 会在新建消息上注入权威 `routePolicy`。以下表达不要求员工额外写“客服”或“配套”：

- “创建内容维护工单”“创建内容工单”或“创建 T3 工单” → 客服工单 + T3 内容维护；消息同时出现“检查原因”、异常描述或 Sold Out 时仍保持 T3。
- “创建 T5 工单/功能建议工单” → 客服工单 + 需求池。
- “创建客户刷卡机工单” → 客服工单 + 客户刷卡机。
- “创建风控处理/Chargeback 工单” → 客服工单 + 风控处理。

只有明确包含“单独、独立、仅、只创建”或明确不要客服主单时，才只创建相应业务工作项。附件、OCR、引用文字和旧草稿不得把 authoritative `customer_bundle` 改成 standalone。

上述 key 是 2026-10-02 至 2026-10-03 在线定位快照。每次提交前必须刷新客服选项、目标类型、创建字段、模板、关联字段和涉及的角色/枚举元数据；字段缺失、禁用或目标类型不符时停止对应联动，不得借用其他字段。

T1/T2 继续按 [客服工单与阻断性问题联动](customer-service-blocking-linkage.md) 处理。T4商务类、内部跟进处理和客户情绪处理/公关危机不自动创建其他类型；用户显式要求独立创建时走普通全类型路由。

## 通用边界

- 一条来源消息形成一个 bundle，保存客服工单 ID、各目标工作项 ID、两侧关联、附件和每一步状态。同一 `source_message_id` 只续跑未完成步骤，禁止重建整组。
- T3、T5、客户刷卡机和风控处理统一采用严格 bundle 门禁：客服与所有命中目标的创建必填值、模板和查重结论全部确定前，不创建其中任何一张。飞书项目没有跨工作项事务，因此门禁通过后的真实写入仍是顺序 API；先创建并回读客服，再把客服 ID 写入新目标反向关联并回读，最后回写客服外向关联并回读。若第一张成功而后续目标或关联失败，状态只能报告“部分完成”，并使用已保存 ID 续跑缺失步骤，不能删除、重建或把单客服单报告为完成。
- `field_5e764e` 是多选；同时命中多个已授权选项时，必须在同一预览中逐项完成必填检查和查重。任一命中目标仍缺事实时，整个 bundle 保持未提交并一次性列出全部缺项；不得先创建客服工单或其他已经完整的目标。
- 每个目标类型独立查重。只有来源消息、已关联客服工单或稳定业务键精确命中时才复用；标题相似仍须让员工选择“复用”或“仍创建”。
- 复用历史目标项时，只把目标 ID 写入本轮新建客服工单；不得在没有具体更新授权时修改历史目标项的反向关联或其他字段。
- 新建目标项时，在创建请求中写入客服工单反向关联；回读成功后再将目标 ID 回写到本 bundle 的客服工单。两侧都必须回读验证。
- 附件在客服工单和目标项中分别归档到各自语义匹配的附件字段；一次上传结果不能跨工作项复用。目标没有合适字段或证据语义不符时保留客服附件并报告，不改发评论。
- 跨类型同义字段采用“有值才复制”：只有客服来源值存在、目标字段在线可用且字段类型/枚举兼容时才写入；来源为空、字段停用或不兼容时跳过，不阻塞目标工单。员工为目标工单明确提供的值优先，禁止用客服值覆盖。
- 这四种联动均不通知 Yoko；只有新建的阻断性问题执行 Yoko 交接。

## T3 → 内容维护

目标类型当前为 `67df87a8baf45c9c247ba778`，普通请求使用“默认内容维护类型”；只有员工明确说 QA 单独流程时才使用 QA 模板。

自动映射：

- 名称 `name` ← 客服工单名称。
- 任务描述 `description` ← 客服描述、要求和交付说明。
- 客户管理 `field_1e7f65` ← 客服已唯一核实的 CRM ID。
- 问题来源 `field_2398ed` ← 客服 `field_20a3c6` 有值且在线选项兼容时原值复制。
- 特殊情况备注 `field_ce6397` ← 客服 `field_4e18a5` 有值时原值复制。
- 工单问题等级 `field_00ae6f` ← 客服 `field_636ce3` 原始星级；与转换后的内容优先级同时保留。
- 商家问题提出人 `field_91fbb2` ← 客服同名字段有值时原值复制。
- 预计完成时间 `field_47cd28` ← 员工明确日期优先；否则复制客服 `field_8c5e5f`；两者都没有时使用 bridge 注入的本轮墨尔本业务日期（当天），不得再补问。
- 客服工单 `field_7e7ab1` ← 本 bundle 新建客服工单 ID。
- 附件 `field_581e1d` ← 同一 bundle 中属于内容制作要求或参考素材的附件。
- 制作人角色继续按主 Skill 的可信群名轮班规则动态分配；每张工单只写入本轮选中的一位制作人，同一草稿保持绑定，不能用提交人或登录人代替。
- 优先级 `priority` ← 客服工单等级：4 星→Q0、3 星→Q1、2 星→Q2、1 星→Q3。写入前按在线名称匹配 option_id；员工明确给出 Q 等级时以其明确值为准。

客服工单没有明确星级时按主技能默认三星，因此本分支默认映射到 Q1；这不是内容维护独立的默认优先级。员工明确给出客服星级或内容 Q 等级时，按上述优先顺序覆盖。

“是否需要确认人确认”不能从客服等级猜测。员工明确选择时优先；否则结合本轮文字和图片/视频证据自动判断：明确出现复杂任务、重点商家、独立词 KA、VIP、Google/谷歌预约、游乐场、复杂餐饮或等价的高复杂度、多环节内容制作任务时写“是”，其余简单任务写“否”，不再常规补问。写“是”时必须从可信来源群名的 `确认：` 段取得确认人，刷新角色和用户后写入“确认人”角色；确认名单、角色或用户不能唯一解析时保留整个 bundle，不创建。写“否”时不写确认人角色。内容模板、制作人、确认设置、优先级映射或 CRM 无法确定时保留整个 bundle，不创建客服工单或内容维护单。

## T5 → 需求池

目标类型当前为 `67ee41797f03010701cea7c6`。模板沿用需求池既有路由：普通功能建议用常规评估，明确付费开发/报价用付费开发评估，明确独立 UI/UX 或综合设计用综合设计任务；语义不清时只问模板。

自动映射：

- 名称 `name`、描述 `description` ← 客服问题和期望。
- 客户管理 `field_5cd576` ← 客服已唯一核实的 CRM ID。
- 客服工单 `field_9fc721` ← 本 bundle 新建客服工单 ID。
- 附件 `field_62493b` ← 同一 bundle 的需求说明或参考附件。
- 客服系统优先级 `priority` 已明确填写 P0/P1/P2 时原值复制；客服星级不自动换算成需求优先级。

名称、模板和查重结论齐全后该目标才就绪；优先级未提供时保持空值，不编造。未就绪时保留整个 bundle，不先创建客服工单。

## 客户刷卡机 → 客户刷卡机工单

目标类型为 `684b899ff9f859147aeca7dd`，使用“默认客户刷卡机类型” `3113731`。2026-10-03 在线核对的双向关联字段为：客服“关联刷卡机” `field_baa8cb`，刷卡机“关联客服工单” `field_928eb4`。两边字段都必须在提交前按名称、类型和关联目标重新核验。

自动映射：

- 名称 `name`、描述 `description` ← 客服工单名称与描述。
- 客户管理CRM `field_7bb02e` ← 客服已唯一核实的 `field_5fe6c7` CRM ID。
- 优先级 `priority` ← 客服系统优先级已明确填写 P0/P1/P2 时原值复制；不从星级换算。
- 关联客服工单 `field_928eb4` ← 本 bundle 新建客服工单 ID。
- 申请资料附件 `field_490c5f` ← 同一 bundle 中属于刷卡机申请资料的附件。

下列创建必填值没有业务默认值，只能从员工正文或附件中的明确事实提取：刷卡机点数 `field_9ef04c`、是否有月租/月费 `field_250a31`、刷卡机数量 `field_a9ddae`。预估刷卡机准备完成时间 `field_73f715` 在员工未明确时默认本轮墨尔本当天，不再列为缺项。其余任一项缺失时，一次性补问所有缺项，并保持客服与刷卡机为同一未提交草稿；不得先创建客服工单。

两张草稿同时就绪后，先完成两类独立查重。精确命中已有刷卡机工单时复用，并只把其 ID 写入本轮新客服工单；没有精确命中时，创建客服工单并回读，再创建刷卡机工单且在创建请求中写入 `field_928eb4`，最后把刷卡机 ID 回写客服 `field_baa8cb`。最终只有在客服工单、刷卡机工单或已复用目标、以及客服外向关联均回读成功时才报告完整完成。

## 风控处理 → 风控处理工单

目标类型当前为 `6a7bbb6b50cf1f8304fedf79`。明确 Chargeback/拒付时使用 Chargeback 流程；其他风控事项使用日常风控跟进流程。无法判断模板时询问。

自动映射或提取：

- 名称 `name`、描述 `description` ← 客服工单名称与描述；描述为空时跳过。
- 客户管理 `field_09ca04` ← 客服已唯一核实的 CRM ID。
- 客服工单 `field_4bf86b` ← 本 bundle 新建客服工单 ID。
- 附件 `field_eb7afd` ← 同一 bundle 中属于本次风控事项的一般证据附件；仍需与 MW 通知截图分别按语义归档。
- Pisell 订单号、Chargeback 金额、风控来源和 Chargeback 原因仅从员工原文或附件中可核实的明确内容提取。
- “MW 通知截图”只接受本 bundle 中语义明确的 MW/风控通知或交易证据图片；普通聊天截图不能冒充。
- 创建隐藏角色“当前处理的负责人”仍须按风控规则唯一解析；不能默认当前登录人。

Chargeback 创建字段要求订单号、金额、来源、原因、MW 通知截图、模板和负责人。任何一项缺失时保留整个 bundle 并一次性补问，不创建客服工单或风控工单，也不通过占位值创建。日常风控模板提交前按本轮在线元数据重新判定必填项。

风控工作项创建后继续执行专项流程就绪检查。员工在原客服消息已经提供“问题分析”节点六项值时可在本 bundle 授权范围内写入并回读；未提供时报告 `awaiting_node_input`，不得编造或自动流转节点。

## 写入顺序与恢复

1. 刷新客服及所有命中目标的元数据，构造每张草稿并独立查重；预览同时列出将新建/复用的工作项和仍缺信息。只有客服及全部命中目标都已就绪才通过门禁；任一缺项都停止在草稿阶段，不执行任何外部创建。
2. 创建并回读客服工单。失败则停止，不创建任何配套项。
3. 对每个信息完整的目标依次复用或创建并回读；新建目标在创建时写入客服反向关联。
4. 将每个目标 ID 分别写入本 bundle 客服工单对应关联字段，并回读验证；不能用一次覆盖写入清空其他关联。
5. 分别归档附件、检查每张工作项当前节点，并返回所有链接与实际状态。

部分失败时保留已创建 ID，只修复缺失目标、关联、附件或节点字段；禁止删除、回滚、重建或自动重放整个 bundle。
