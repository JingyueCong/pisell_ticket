# 客服工单与阻断性问题联动

适用空间：`v2qint` / Pisell项目管理。此规则仅适用于新建客服工单时，“对应问题类型”包含当前在线选项 **T1核心阻断性问题** 或 **T2非核心阻断性问题类流转升级** 的场景。用户于 2026-10-02 明确要求为这两类客服工单自动建立或复用阻断性问题，并自动补齐可可靠生成的必填字段。

提交前刷新两个类型的模板、创建字段、关联字段、枚举和角色元数据。快照只用于定位：客服工单指向阻断性问题的字段当前为 `field_d1511f`，阻断性问题指向客服工单的字段当前为 `field_295507`；不得在在线字段缺失或目标类型不符时继续写入。

## 触发与授权边界

- 当员工只说“创建工单”，且本轮文字或截图明确为企业微信/企微群等商家来源时，先路由为客服工单；已有功能异常只决定客服的 T1/T2 分类，不得直接替代为独立阻断性问题。员工明确要求“阻断性问题/T-BUG”时不适用此默认入口。
- T1/T2 是自动联动阻断性问题的唯一触发项；T3 内容维护、T5 需求、客户刷卡机和风控处理按 [客服工单与业务工作项联动](customer-service-paired-workitem-linkage.md) 进入各自目标类型，不得创建阻断项。T4、内部跟进和客户情绪/公关仍只创建客服工单。
- 客服工单未明确星级时使用主技能授权的三星默认值，但配套阻断性问题的 Lv 仍由 T1/T2 决定，禁止把三星转换成阻断 Lv。
- 这是已授权的客服跨类型联动之一。一次来源消息形成一个 bundle，记录客服工单 ID、阻断性问题 ID、两侧关联和 Yoko 交接状态。
- 联动目标是“存在且关联一张对应阻断性问题”，不是无条件每次新建。多个客服工单可以关联同一已核实的阻断性问题。
- 用户说只预览、暂缓联动或取消时不写入。此授权不允许批量补建历史客服工单，也不允许修改无关历史字段。

## 自动字段映射

先按客服规则补齐客服工单本身，再构造阻断性问题草稿：

| 阻断性问题字段 | 来源或规则 |
|---|---|
| 名称 `name` | 复用客服工单的问题名称，不加店铺、终端或联动前缀 |
| 客户管理 `field_ef7f33` | 复用客服工单 `field_5fe6c7` 已唯一核实的 CRM 工作项 ID |
| 店铺id `field_8318ee` | 优先用员工明确提供的店铺号；缺失时仅可从已回读的 CRM 名称开头提取明确店铺号，否则询问 |
| 页面链接及说明 `field_41737a` | 复用客服工单描述和已提供链接 |
| 描述补充 `field_c28813` | 简洁复用现象、影响、已尝试操作和附件说明，不推断根因 |
| 反馈类型 `field_10c5ea` | 客服“问题来源”为企业微信、WhatsApp、客服专用邮箱、飞书商家群、Zendesk 或线下销售/运营转述时写“商家反馈”；只有原文明确说明员工内部发现时才写“内部发现” |
| 内部发现人 `field_c21b7f` | 仅在反馈类型为“内部发现”时按主技能规则解析原始收单消息发送者；商家反馈不询问、不解析、不写入 |
| 终端详情 `field_afbac9` | 从正文与本单图片可靠识别当前合法选项；仍无法确定时只询问终端，不默认第一项 |
| 客服工单 `field_295507` | 写入刚创建的客服工单 ID；复用历史阻断性问题时不借此授权修改其其他字段 |
| 缺陷相关截图或视频 `field_7ea900` | 将同一 bundle 已绑定业务附件单独上传到阻断性问题并回读；客服工单附件仍写自身附件字段 |

下列值属于本联动的已授权自动值，写入前仍按在线显示名称匹配 option_id：

- 客服 T1 → 阻断性问题优先级“Lv1-紧急主流程中断”；客服 T2 → “Lv2-紧急核心高优先”。员工显式给出的合法 Lv 等级优先。
- 阻断性问题类型 → “技术缺陷（T-BUG）”。如果原文明确是功能缺口、配置、教育、性能或其他当前合法分类，以员工事实为准，不强制改成 T-BUG。
- 反馈类型不再统一默认：上述客服外部渠道 → “商家反馈”；明确内部发现 → “内部发现”。发生时间点和预期修复截止时间 → 同一个提交时当前时间；页面说明 → 客服描述。
- APP版本号、软件版本和硬件详情有可靠来源时照实填写。如果本轮在线创建协议实际要求非空而客服消息没有这些事实，可填“未提供（客服工单联动，待技术确认）”，不得编造版本号或设备型号；预览和结果中标明这是占位信息。

客户、店铺或终端无法唯一确定时不能用占位值代替，因为它们决定问题归属和研发定位。只有反馈类型为“内部发现”时，提交人身份才属于必填解析范围；此时无法唯一确定也不能占位，并只询问提交员工姓名/邮箱。反馈类型为“商家反馈”时禁止因此阻塞或补问员工身份。一次性询问实际仍缺项，补齐后继续同一 bundle。

## 两类查重

1. 客服工单仍按客服类型查重。
2. 阻断性问题独立在阻断类型内查重，优先使用来源消息、已关联客服工单、CRM、完整店铺号、规范化问题名称、终端和相近发生时间。
3. 只有来源或稳定业务键精确命中时才复用现有阻断性问题。标题相似只列候选并等待“复用”或“仍创建”，不得自动合并。
4. 同一来源消息已有 bundle ID 时只回读或修复未完成步骤，禁止再次创建任一侧。

## 写入顺序与部分失败

在两张草稿的必填值、目标和查重结果都确定后，预览同时列出将创建/复用的两张工单和自动字段：

1. 创建并回读客服工单；失败则停止，不创建阻断性问题。
2. 若精确命中已有阻断性问题，将其 ID 写入新客服工单的 `field_d1511f`。不重新通知 Yoko，也不修改该历史阻断项的其他字段；需要主动改写历史阻断项时仍须具体授权。
3. 若没有精确命中，创建阻断性问题，并在创建请求中用 `field_295507` 关联第 1 步的客服工单；回读验证后，将阻断性问题 ID 回写到本 bundle 刚创建客服工单的 `field_d1511f`。这一次回写属于本联动的新建 bundle 授权。
4. 分别归档和回读两张工单的附件与关键字段，再分别执行当前节点就绪检查。
5. 只有本 bundle 新创建的阻断性问题按主技能规则通知 Yoko。客服工单本身不单独通知。

任何后续步骤失败时保留已经创建的工作项，保存实际 ID 并明确报告“部分完成”和待修复步骤；不得回滚、删除、重建或自动重放整个 bundle。重新收到指令时先按来源状态和已保存 ID 回读，再只修复缺失关系、附件或通知。

最终结果同时给出客服工单和阻断性问题的可点击链接、是否新建/复用、两侧关联验证、各自流程就绪状态，以及 Yoko 通知结果。
