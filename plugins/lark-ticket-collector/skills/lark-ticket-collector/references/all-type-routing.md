# Pisell 全类型路由

适用空间：`v2qint` / Pisell项目管理。在线快照更新至：2026-09-29。机器可读目录见 [work-item-catalog.json](../../../workspace/configuration/work-item-catalog.json)。提交前必须刷新项目、类型、创建字段、模板及本次涉及字段；目录用于类型发现、解释和离线测试，不替代在线元数据。创建后的完整性规则见 [流程就绪检查](workflow-readiness.md)。

## 覆盖范围

Pisell 当前返回 22 个类型：

- 16 个标准创建类型：开发进度、产品功能、客户管理CRM、商机跟进记录、内容维护、阻断性问题、版本迭代、需求池、验收记录、客户刷卡机、客服工单、预工单、硬件库、组件开发、数据基建、风控处理。
- 2 个启用的专用域：图表、任务。图表使用 chart 域；任务是子任务，创建时必须有父工作项或节点上下文并使用 subtask 域，不能当作独立顶层工单猜测创建。
- 4 个已停用类型：需求、缺陷、XZero平台开发、Pisell OS。允许查询历史项和解释状态，不允许新建；不得偷偷改投其他类型。

## 类型识别

显式类型名称、api_name 或唯一别名优先。常见映射：

| 用户表达 | 目标类型 |
|---|---|
| T-BUG、阻断、已有功能异常、报错 | 阻断性问题 |
| 需求池、功能建议、新功能、产品改进 | 需求池 |
| 客服工单、客户咨询、售后、运营跟进 | 客服工单 |
| 开发任务、研发任务、产品开发 | 开发进度 |
| 里程碑、版本拆分 | 产品功能 |
| CRM、客户档案、新建客户 | 客户管理CRM |
| 商机、销售机会、销售跟进 | 商机跟进记录 |
| 内容维护、内容制作、代制作 | 内容维护 |
| 发版、上线、版本发布 | 版本迭代 |
| 验收问题、产品验收、技术验收 | 验收记录 |
| 刷卡机申请、POS机申请 | 客户刷卡机 |
| 预工单 | 预工单 |
| 硬件设备、Device、硬件采购 | 硬件库 |
| 组件开发、组件升级、组件存档 | 组件开发 |
| 数据基建、数据工程 | 数据基建 |
| Chargeback、拒付、日常风控 | 风控处理 |

“需求”“客户”“任务”“硬件问题”等宽泛表达可能命中多个类型，必须列出最相关候选让用户选择，不能默认第一项。例如“需求”至少可能是需求池、产品功能或开发进度；“客户问题”可能是客服工单、CRM 或商机跟进。客服工单已明确选择 T1/T2、T3 内容维护、T5 需求、客户刷卡机或风控处理时，按对应联动规则创建或复用配套项；只有这些明确选项属于已授权的跨类型自动创建例外。

来源证据也是路由事实：员工只说“创建工单”且本轮文字或截图明确来自企微等商家渠道时，先路由为客服主单草稿。商家反馈中的已有功能异常用于把客服“对应问题类型”分类为 T1/T2，并触发配套阻断项；不能仅因出现“卡慢、异常、报错、无法使用”就绕过客服主单。绿色配套类型必须等客服及全部目标草稿就绪后再开始外部创建。员工明确指定“阻断性问题/T-BUG”或其他 Meegle 类型时，显式类型仍优先。

## 标准创建流程

1. `project search` 唯一验证 `v2qint`，再用 `meta-types` 精确匹配目标 type_key 并核对当前启用状态。
2. 并行读取目标类型的 `meta-create-fields`、`meta-fields(field_keys=["template"])`，以及本次涉及字段；需要人员或角色时同时读取 `meta-roles` 和 `user search`。
3. 标准工作项至少解析名称与模板。即使 `meta-create-fields` 漏掉核心字段，也必须从模板元数据核验真实模板；目录中标记 `platform-core` 或 `meta-fields-hidden-from-create-list` 的字段说明曾观察到元数据不完整，不能因此跳过。
4. 枚举、布尔、日期、人员、关联项和附件没有跨类型默认值。只使用提交人明确提供的值、已核实适用的平台默认值，或本技能中针对特定类型记录的用户授权默认规则。不得把样例工单或第一项当默认值。
5. 只询问仍缺的必填项与模板歧义；给出类型、模板和实际写入字段的简短预览。满足持续新建授权且无重复歧义后自动创建。
6. 创建后回读 ID、名称、类型、模板、`template_version`、当前节点和关键字段，再对所有当前节点执行 `list-state-required --mode unfinished`。有未完成必填项时只能报告“已创建，待补充”；未实际验证创建或节点就绪的类型不得声称相应级别已通过。

## 特定类型规则

- 阻断性问题、需求池和客服工单已有真实端到端证据，详细字段、隐藏必填项和模板规则见 [三类已验证工单规则](multi-type-routing.md)。
- 内容维护新建单的“制作人&交付人”按 `CONTENT_PRODUCER_SOURCE_CHAT_ID` 与 `runtime.json#content_maintenance.producer_role_source` 的解析规则动态取得：优先使用 bridge 注入的可信群名与 producer_names；可信数据已解析时不得再索取制作人。环境变量缺失、读取失败或解析冲突时停止自动创建并询问。
- 客服工单的“下次跟进时间”是“对应问题类型＝内部跟进处理”时才出现的条件必填项。该分支曾被创建接口确认为必填，不能因创建字段接口漏报而删除；其他客服类型不得补问或写入。
- 客服 T1/T2 联动阻断性问题的规则见 [客服工单与阻断性问题联动](customer-service-blocking-linkage.md)；T3 内容维护、T5 需求、客户刷卡机和风控处理的规则见 [客服工单与业务工作项联动](customer-service-paired-workitem-linkage.md)。全部绿色类型都先完成整个 bundle 的必填校验和独立查重，再开始顺序创建并验证双向关联；T4 商务、内部跟进和客户情绪/公关不自动创建配套项。
- 阻断性问题是唯一自动进入 Yoko CLI 根因拆解交接的类型；T1/T2 客服 bundle 也只交接其中新创建的阻断项，客服工单本身不交接。其他类型除非另有明确授权和接收配置，只返回链接与当前节点。
- 图表不是普通 Ticket；使用 chart 查询/管理域。子任务必须先获得父工作项或节点，使用 subtask 域。二者的 `meta-create-fields` 为空时不能虚构顶层创建协议。
- 已停用类型只能查询历史项。用户要求新建时说明已停用并展示可能的启用类型候选，由用户明确选择，不能自动改投。
- 风控 Chargeback 已验证存在创建元数据未返回的必填角色“当前处理的负责人”，且首节点“问题分析”有 6 个必填业务字段；必须读取 [流程就绪检查](workflow-readiness.md) 的专项 profile，不能复用首次失败请求或默认当前登录人。

## 附件路由

提交前按目标类型刷新 `multi-file` 字段。只有一个附件字段时可使用该字段；存在多个字段时按附件语义精确匹配：合同进合同备份、付款证明进付款截图、MW 通知进 MW 通知截图。普通证据若存在唯一名称为“附件”的字段可用该字段；同名字段不唯一或语义不清时必须询问。

没有附件字段的类型只记录“该类型当前未暴露可写附件字段”，不得改发评论、借用其他类型字段或跨工单归档。所有附件继续采用先上传、保留旧值、合并去重、整体写回并回读的协议。

## 查重和结果

查重限定在目标类型内；精确来源或业务键命中时复用，标题相似只列候选。宽泛类型尚未消歧时不能跨多个类型同时创建。结果必须返回可点击详情链接、实际类型、模板版本和当前节点；专用域或停用类型则明确说明支持边界和所需上下文。
