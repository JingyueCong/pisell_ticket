# Pisell 阻断性问题收单字段

适用：`v2qint` 的“阻断性问题（Blocking Issues）”收单、下拉解析和配置维护。
基础表单核验日期：2026-09-07；最新在线端到端核验：2026-09-28。来源：[用户指定样例工单](https://project.feishu.cn/v2qint/bug/detail/7100875886)、用户提供的创建表单与客户下拉截图，以及 Meegle 在线元数据与测试单回读。2026-09-28 已翻完字段分页，共 87 个定义；测试单 `_all` 回读成功。

此文和 [配置快照](pisell-intake-schema.snapshot.json) 的 key / ID 仅用于定位核对，不能作为跨空间或永久默认值。创建条件表达式未由此次接口返回，不能声称已验证所有分支。截图里的客户“你可能想选”只是动态推荐，不能缓存为全量客户选项。

## 目标类型

- 空间：Pisell项目管理；simple_name `v2qint`；核验的 project_key `67c68170af5c921068953f8b`。
- 类型：阻断性问题（Blocking Issues）；URL/API 别名 `bug`；type_key `67df88cf656f61b9b41455d3`。
- 模板字段 `template`（名称“bug池类型”），此次唯一选项为“默认流程类型” / `2769525`。
- 同空间还存在旧的“缺陷 issue”，不能按英文 bug/issue 近义关系选错类型。

## 模板版本核验

用户于 2026-09-10 要求后续使用新模板。`template` 是模板 ID，`template_version` 是实例的流程版本；模板名称/ID 不变不代表流程未更新。

本轮已核实：

- 当前唯一可用模板仍为“默认流程类型” / `2769525`。
- 2026-09-28 以当前模板创建测试单 #7126656340，平台实际写入 `template_version=166`，当前节点为 `task拆解指派`。这是创建后回读证据，不把 166 写成永久默认，也不把实例版本冒充模板发布目录。
- 当前 CLI 的 `workitem create` 未暴露独立流程版本选择参数；元数据中的 `template_version` 仅证实可读取，不能据此推断可在创建字段里手写版本。
- 当前浏览器新建表单（`/v2qint/bug/create`）仍显示名称、客户管理、优先级、阻断性问题类型、发生时间、店铺、页面说明、终端详情、预期修复截止时间、反馈类型必填。此次仅打开空白表单读取，没有创建或保存云端草稿。
- 2026-09-28 当前字段元数据共 87 项；字段集合会随配置演进，不能仅凭字段存在将其判为创建必填。后续拆解节点的字段要求仍需按节点元数据核验。

每次新建时：

1. 同一认证 profile 下刷新 `meta-fields` 的 `template`、`template_version`、创建涉及字段，以及 `meta-create-fields`，不复用旧创建请求。若模板选项变化，按用户指定的新模板及业务类型唯一匹配。
2. 有模板发布列表/版本管理页面时，以当前可用的最新已发布版本为准；CLI 未提供发布目录时，可用下列 MQL 查询当前实例最高版本作为核验基线，记录为“最新已观察实例版本”，不宣称已检查未发布草稿或全部模板发布状态。
3. 使用本轮有效模板 ID 走正常新建协议；不传未经证实可写的 `template_version`，不锁定旧实例版本。创建后显式 `workitem get --fields '["template_version"]'`，保存实际模板 ID/版本及核验结果；低于已核实发布版本或当前实例基线时，报告版本不符并核实创建入口，不重建、不擅自迁移旧单。
4. 本规则适用于待提交草稿；历史工单仅追加反馈时保留其模板版本。用户要求后续用新版，不等于授权批量升级历史工单。

MQL（空间、类型、字段仍需先用本轮元数据核验；通过安全参数传递）：

```sql
SELECT `work_item_id`, `template`, `template_version`, `start_time`
FROM `<project_key>`.`<type_key>`
ORDER BY `template_version` DESC, `start_time` DESC
LIMIT 1
```

## 必填与条件差异

此次 `meta-create-fields` 用 `bug` 别名和真实 type_key 查询结果一致：
- 返回 11 项，均标记 `is_required: 1`，`default_value.value: null`。
- 与截图重合的 7 项：紧急程度优先级、阻断性问题类型、发生时间点、店铺id、页面链接及说明、终端详情、反馈类型。
- 另外返回 APP版本号 `field_2893b2`、软件版本 `field_1e9d61`、硬件详情 `field_c82e24`（均 text）和内部发现人 `field_c21b7f`（multi-user）。
- 截图有星号但该返回未列出：名称、客户管理、预期修复截止时间。模板仍是创建协议需要的字段。

这说明清单不能单独还原当前 UI 的所有要求；可能涉及条件或接口范围。2026-09-28 在线创建测试进一步证实：即使 `meta-create-fields` 未列出客户管理，不传 `field_ef7f33` 仍会被接口以 `ErrFieldRequired` 拒绝，且没有产生工作项。补入已回读确认的测试 CRM 记录后创建成功。因此当前 `v2qint` 默认流程中客户管理必须在提交前解析；不要声称四个额外字段在所有场景都必填，也不要因 API 未列出就忽略表单或创建接口明确的必填项。

运行时处理：
1. 先解析用户已给值、客户关系、终端、类型和反馈来源，再核对适用条件；有当前表单/模板条件证据时记录依据。
2. 暂不能核实的字段标为“条件待核实”，集中指出具体差异；不要让用户无条件填写全部版本/硬件/发现人，也不要试建业务工单验证。
3. 页面说明复用问题描述；反馈类型填内部发现；优先级按显式等级或订单/金额 Lv2、其他 Lv3；两个日期默认提交时当前时间。这些已有用户授权的值不再补问。只集中询问仍缺的适用必填信息或终端歧义，例如“WebPOS 是 IOS 还是 Android？”
4. 提交前读取一次当前时间，两个业务日期字段共用其毫秒时间戳，默认以当前会话时区展示（此工作区 Asia/Shanghai）；草稿不冻结旧时间。描述注明“按收单约定填写当前时间”。原文实际发生时间仍按事实保留；用户后续明确要求按具体日期填写时遵从最新指示。系统创建时间由平台生成。
5. 内部发现人按用户规则填写发起提交者：自动提交取原始收单消息发送者，明确接手提交则取该提交指令发送者；补图、配置说明及引用作者不改变提交人。用其 bridge 身份信息或 lark-contact 查询得到姓名/邮箱，再经 `meegle user search` 解析为 userkey；通讯录无权限可从原始提交消息的 sender_name 取得姓名。bridge senderId 是飞书 open_id，不能直接写入，也不能默认等于 CLI 登录人。唯一匹配后写入 JSON 字符串化的 userkey 数组；只有无法识别或重名时才补问姓名/邮箱。2026-09-07 实际提交已明确返回 `ErrFieldRequired: 内部发现人(field_c21b7f) 必填`；该错误不证明其他版本/硬件字段是否必填。
6. 默认值只接受已核实适用的平台配置或用户明确制定的规则；本次返回的 null 不构成默认值。参考工单的等级、日期、版本和人员不是默认规则。

## 下拉匹配

先消除大小写、空白和显然等价的写法，再匹配同一字段的 option_name。找不到或不唯一则返回候选。禁跨字段复用同名 option_id。

- `webpos iOS` → 终端详情“WebPOS IOS”；`webpos Android` → “WebPOS Android”。
- 仅 `webpos` 已足以识别产品端；本单上下文有系统信息时直接解析，无需问页面模块。当前元数据及用户截图均有 IOS/Android 两个选项，没有通用“WebPOS”选项；缺少系统信息时只问系统，不默认 IOS、不同时勾两个。未来若元数据提供唯一通用项可按其匹配。`web端` 不能直接当作 WebPOS。
- 单独“iOS”不等于 WebPOS IOS，单独“Kiosk”不能区分原生安卓和 Web Kiosk。
- “WebPOS iOS 的 booking”表示端与模块；不要仅因 booking 一词再勾“在线店铺（预约）”。
- 多选仅包含用户明确涉及的端。不要把历史单选“缺陷终端详情 ”（`field_d4c9a3`）或“缺陷终端类型”（`field_3a675e`）当成当前字段。
- 优先级使用 `priority`，不使用另一旧字段“紧急程度”（`field_6a180f`）。
- Lv1/Lv2/Lv3（大小写不敏感）分别匹配 Lv1/Lv2/Lv3 显示值，其他合法等级同理；显式等级优先于推断。未指定时按用户规则：问题实际涉及订单或金额（含支付、退款、扣款、订单状态或金额）用 Lv2，其他用 Lv3；否定或背景提及不算。仅从描述分类，不做根因调查。示例：“Lv3 支付失败”仍 Lv3；“重复扣款”→Lv2；“订单状态异常”→Lv2；“按钮错位”或本会话“测试bug”→Lv3。
- 用户于 2026-09-07 明确约定：通过本技能新建的阻断性问题，反馈类型统一填“内部发现”，该类型内所有问题分类均适用，当前未提交草稿同样适用。这是用户指定的收单规则，不是从发送者身份推断；写入前按当前选项名称解析 ID。原始反馈来源仍按事实保留，已有工单的反馈类型不自动覆盖。
- 问题来源与反馈类型不同；内部飞书会话不能自动归为“飞书商家群”。

## 关联下拉：客户管理与客服工单

这两个控件没有固定 options，使用 `related_work_item_info` 指定的目标空间/类型查询；实际返回的类型键为 `work_item_type`，兼容工具版本可能使用的 `work_item_type_key`。

- 客户管理目标：客户管理CRM，类型快照 `67df84a32e42950cb0195cba`。

MQL 形状（变量均来自本轮元数据和用户输入；参数安全传入，不把含反引号的 MQL 拼进双引号 shell 命令）：

```sql
SELECT `work_item_id`, `name`, `work_item_status`
FROM `<project_key>`.`<related_type_key>`
WHERE `name` = '<完整名称>'
LIMIT 10
```

出现分页必须继续处理候选页或缩小检索，不以第一页声称全局唯一。CLI 返回值在 `data` 各组的 `moql_field_list` 内，按 `key` 与 `value_type` 读取，而不是把顶层 `list` 的分组统计当客户记录。

## 写入与附件

按当前 CLI 协议转换；本环境通用 Meegle 写入文档规定协议层 `field_value` 为 STRING：文本直接传，单选传 option_id 字符串；普通 multi-select 用 JSON 字符串化的对象数组 `[{"option_id":"<id>"}]`，multi-user 用 userkey 字符串数组，关联多选用数字 ID 数组；日期为毫秒时间戳字符串。终端详情用纯 ID 字符串数组曾返回 `field_afbac9 is illegal`，按对象数组修正后接口继续校验内部发现人。关联读出的 `[{id,name}]` 和枚举 `{label,value}` 不是写入格式；不要直接回写整个展示对象。

收单正文分别落在“页面链接及说明”和“描述补充”。描述补充以问题现象和影响为首句，必要时补充已尝试操作、最短复现或期望（归纳内容标注待确认）；时间默认依据仅一句，详细来源、身份映射、查重、模板版本和附件哈希均留本地。后续仅在用户授权更新现有描述时执行简化，不自动改写历史工单。
