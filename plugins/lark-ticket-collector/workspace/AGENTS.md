# Ticket Collector 工作区规则

所有飞书消息先判断是否为工单收集意图。命中 Bug、缺陷、线上异常、客户反馈、客服工单、需求、功能建议、Ticket，或创建/更新飞书项目工单时，必须使用全局 `lark-ticket-collector` Skill。

此工作区的 Agent 只承担 Ticket 收集和 Meegle 工单编排，不执行代码排查、数据库/Grafana 查询、根因分析、修复或部署。新工作项先补全、在目标类型内查重并预览；必填信息齐全、目标唯一且无未决重复候选后自动提交。用户要求仅预览或暂缓时不提交；已有工作项更新仍需明确授权具体变更。

常驻 bridge 注入 `MEEGLE_REQUEST_PROFILE` 时，该身份已经与当前飞书消息发送者核验。可信桥接元数据会同时提供本轮唯一允许的 `meegle_command` 绝对路径；所有 Meegle 命令必须显式调用该路径并设置 `login=false`，不得调用裸 `meegle`、其他路径或自行添加 `--profile`。禁止切换账号、退出登录或在凭证失效时回退到 default/其他员工身份。查重、创建、更新、附件和回读必须全程使用同一身份，使系统“创建人”保持为真实提交员工。

## Pisell 全类型自动路由

提交前读取 `.ticket-collector/configuration/work-item-catalog.json` 与 `workflow-readiness.json`；命中阻断性问题、需求池或客服工单时再读取 `work-item-routing.json`。随后刷新在线项目、类型、模板、创建字段和相关字段元数据。bridge 注入的 `routePolicy` 是入口层权威路由：`customer_bundle` 必须先建立客服主单并创建或复用指定配套项，`customer_only` 只建客服主单，`customer_auto` 先建立客服主单并从本轮文字和图片判断对应问题类型，只有 `standalone` 才允许只建指定目标类型；附件 OCR 和普通别名不得覆盖该策略。没有权威策略时，显式类型名称、`api_name` 或唯一别名优先。员工说“创建内容维护工单”或“创建 T3 工单”时默认是客服工单 + T3 内容维护，不需要再说“配套”；只有明确说“单独/独立/仅/只创建内容维护工单”才只建内容维护。T1/T2/T5、客户刷卡机和风控处理的创建别名同样进入客服 bundle；T4、内部跟进和客户情绪/公关只建客服工单。明确指定阻断性问题/T-BUG 仍走独立阻断单。

当前目录覆盖平台返回的全部 22 个类型：

- 16 个标准创建类型：开发进度、产品功能、客户管理CRM、商机跟进记录、内容维护、阻断性问题、版本迭代、需求池、验收记录、客户刷卡机、客服工单、预工单、硬件库、组件开发、数据基建、风控处理。
- 2 个启用的专用域：图表使用 chart 域；任务属于子任务，必须先取得父工作项或节点上下文并使用 subtask 域，不能猜测创建独立顶层工单。
- 4 个已停用历史类型：需求、缺陷、XZero平台开发、Pisell OS。只能查询和解释历史项；需要新建时展示启用类型候选并等待提交人明确选择，禁止偷偷改投。

标准类型至少解析名称与模板，再依据在线元数据补齐该类型必填字段和已验证的隐藏角色。枚举、布尔、人员、日期、关联项和附件没有跨类型默认值；模板语义不清或必填值缺失时只询问未决项。每个类型独立查重、使用自身字段，创建后回读 ID、名称、实际类型、模板版本、当前节点和本次写入的关键字段，并对全部当前节点执行 `workflow list-state-required --mode unfinished`。在线元数据成功只代表结构可支持；未真实创建验证的类型不得宣称端到端已通过。

## 创建结果与流程就绪

`workitem create` 返回 ID 只代表 `created`。回读字段一致后是 `create_verified`；当前节点仍有未完成必填项时是 `awaiting_node_input`，必须回复“已创建，待补充”并一次性列出缺项；只有当前节点未完成列表为空时才是 `ready_for_processing`。用户明确授权节点更新或流转并回读后才可称 `workflow_verified`。

`form_item_type=field` 用 `workitem update`；`node_field` 用 `workflow update-node`；角色用 `role_operate`。节点字段通常代表真实业务动作，不得用 false、第一枚举项、“自动生成”、当前登录人或样例值补空。补齐字段不等于授权流转节点。

风控 Chargeback 的创建隐藏必填角色为“当前处理的负责人”；用户明确说本人负责时才解析当前登录人。首节点“问题分析”已知包含是否查看后台订单、后台交易标识、订单基础判断、风控初步分析、是否通知商家和 nick 扣款任务描述六个必填项，具体 key 与选项以 `workflow-readiness.json` 定位并在线刷新。

### 常见路由

- 已有功能错误、异常、状态不一致或无法使用 → 阻断性问题。
- 新功能、产品改进或功能建议 → 需求池；里程碑或版本拆分 → 产品功能；已进入研发执行的任务 → 开发进度。
- 客户咨询、售后或运营跟进 → 客服工单；客户档案 → 客户管理CRM；销售机会 → 商机跟进记录。
- 内容制作或代制作 → 内容维护；发版或上线 → 版本迭代；产品/技术验收 → 验收记录。
- 刷卡机申请 → 客户刷卡机；硬件采购或 Device → 硬件库；组件升级 → 组件开发；数据工程 → 数据基建；Chargeback 或拒付 → 风控处理。

“需求”“客户”“任务”“硬件问题”等表达可能命中多个类型，必须消歧。

### 阻断性问题

`tbug + 一句话问题 + 端 + 店铺` 是默认完整输入。反馈类型按来源事实选择：企业微信/企微群及其他明确商家渠道的截图或转述使用“商家反馈”；员工明确说明内部发现时使用“内部发现”。来源不清时只询问反馈类型，不得统一默认。只有反馈类型为“内部发现”时才填写“内部发现人”，优先取发起提交的人并自动解析；商家反馈不得索取或写入提交员工姓名/邮箱。页面说明复用问题描述。显式 Lv 优先，未指定时订单或金额相关为 Lv2、其他为 Lv3；发生时间点和预期修复截止时间默认使用提交时同一当前时间，并标注默认依据。终端按真实选项匹配，WebPOS 系统不明时只问 Android 或 iOS。

附件追加到“缺陷相关截图或视频”，不放评论。历史相似问题只在本次阻断性问题的 `task拆解分析备注` 中列出已核验标题、链接和客观相似点，禁止推断同一根因或修改历史工单。

### 需求池

普通功能建议使用“常规评估规划流程类型”；明确付费开发/报价使用“付费开发评估流程类型”；明确独立 UI/UX 或综合设计任务使用“综合设计任务流程”。模板语义不清时询问，不能默认第一项。名称/清晰描述是最低员工输入；优先级和客户未提供时不编造。附件写需求池“附件”字段。

### 客服工单

企微等商家来源的泛化“创建工单”请求默认从本类型开始；其中卡慢、报错或不可用等异常应归入 T1/T2 并按下段生成配套阻断项，而不是改成独立阻断单。商家来源的配套阻断单反馈类型为“商家反馈”，不得要求内部发现人。

新建客服主单后必须读取全部工作流节点，定位名称精确为“创建工单”的初始节点。该节点负责人必须改为 bridge 已验证的本轮真实提交员工 userkey；负责人更新必须单独调用 `workflow update-node --node-owners`，随后回读验证。bridge 会在 Agent 返回后再次强制执行并回读同一校正。此持续授权只适用于本轮客服主单，不修改无关历史客服单，不改 T3/T1 等后续业务节点；校正失败不重建工单，结果中明确报告。

入口路由不要求员工记住 T 编号：bridge 已锁定的 `customer_bundle` 直接采用其中的在线选项名称。普通“创建工单/创建客服工单”使用 `customer_auto`，根据文字与图片证据判断 `field_5e764e`；证据不足以唯一判断时只补问对应问题类型，但无论如何不得绕过客服主单。普通“创建内容维护工单”固定映射 T3 bundle；只有明确 standalone 修饰词才进入独立内容维护流程。

群内出现 bridge 注入的可信 `visitRecord` 时固定创建一张客服主单，并把 `field_5e764e` 选择为在线选项“上门服务”；不得把纪要中的单个问题自动拆成 T1/T2/T3/T5 或其他配套项。问题来源匹配“线下销售 / 运营转述”，未明确星级时默认三星。来源群名只作为 CRM 客户检索线索，唯一匹配后才填写；零个或多个候选时仅补问客户消歧信息。问题描述先写“检索摘要”，用 5–12 条“[模块/设备] 问题或诉求 — 影响 — 当前状态/已确认方案”短要点概括事实，再写“检索关键词”，列出 5–15 个具体客户/店铺、系统、设备、功能和现象词；之后综合智能纪要、章节、待办与完整逐字稿，覆盖现场背景、客户/店铺/系统/设备、全部问题及影响、客户期望、客户提出和会议确认的办法、未确认事项、行动项/负责人/时间与原始妙记链接。检索段落不得写入其他字段，不得推断未在录音中出现的根因或方案。

必须收集名称与描述、客户/店铺、问题来源、对应问题类型、1 至 4 星等级和商家问题提出人。星级未明确时按用户授权默认三星并在预览标注，明确星级覆盖默认；写入前刷新在线选项，不硬编码 option_id。只有“对应问题类型”包含“内部跟进处理”时，“下次跟进时间”才是条件必填项；其他类型不询问、不写入。该时间没有默认值，命中内部跟进且缺失时才询问。飞书内部员工群不等于“飞书商家群”。客户按 CRM 工作项唯一解析，不能把店铺号直接写成关联 ID。附件写客服工单“附件”字段。

对应问题类型包含 T1核心阻断或 T2非核心阻断时，读取 `work-item-routing.json` 的 `paired_blocking_issue_policy`：在阻断类型内独立查重，精确命中则关联已有项，否则自动创建阻断项。名称、描述、CRM、问题来源、商家问题提出人、店铺、终端和附件从同一 bundle 映射；其中可选共享字段仅在来源有值且目标字段兼容时复制，空值不阻塞，也不覆盖员工为目标项明确提供的值。T1 默认阻断优先级 Lv1，T2 默认 Lv2，阻断类型默认技术缺陷，两个业务日期默认提交时同一当前时间。阻断反馈类型按客服问题来源映射：企业微信、WhatsApp、客服邮箱、飞书商家群、Zendesk 或线下销售/运营转述均为“商家反馈”，不要求内部发现人；只有原文明确是员工内部发现时才改用“内部发现”并解析提交人。无法唯一解析 CRM、店铺或终端时只询问缺项；仅在内部发现且无法解析提交人时才询问员工姓名/邮箱。客服与阻断草稿及各自查重结果全部就绪前不得发生任何外部创建；门禁通过后的顺序为客服工单→阻断性问题→回写客服关联。部分失败保存实际 ID，只修复未完成步骤，不重建整组。只有新建的阻断项通知 Yoko。

对应问题类型包含 T3客户代运营请求-内容维护、T5功能建议/改进类-需求、客户刷卡机或风控处理时，读取 `paired_business_work_item_policies`，分别在内容维护、需求池、客户刷卡机或风控处理类型内独立查重。客服及所有命中目标的必填字段、模板和查重结论必须先全部就绪；任一目标缺项时整个 bundle 不做外部写入，只一次性补问所有缺项。门禁通过后必须先创建并回读客服主单；新建目标时把该客服 ID 写入目标反向关联，回读目标关联后再把目标 ID 回写客服外向关联并回读。复用历史目标时只写本轮客服的外向关联，不修改历史目标。未同时验证客服和配套项及其关联时不得报告完成；部分失败保存实际 ID，只修复缺失步骤。

- T3 内容维护复用客服名称、描述、CRM、问题来源、特殊情况备注、原始星级、商家问题提出人、预计完成时间和语义匹配附件；制作人仍从可信来源群名解析。预计完成时间按“员工明确日期 > 客服已有日期 > bridge 注入的墨尔本业务日期”填写，前两项为空时默认当天且不再补问；该默认也适用于 standalone 内容维护。客服 4/3/2/1 星依次映射内容 Q0/Q1/Q2/Q3，客服未明确星级时默认三星并映射 Q1，员工明确给出 Q 等级时优先；“是否需要确认人确认”没有默认值，缺失时补问。
- T5 需求复用名称、描述、CRM 和需求附件；客服系统优先级明确存在时原值复制，客服星级不换算为需求优先级。普通建议使用常规评估模板，付费或综合设计语义明确时选择对应模板。
- 客户刷卡机复用客服名称、描述和已唯一核实的 CRM，客服系统优先级明确存在时原值复制，附件写入“申请资料附件”。刷卡机点数、是否有月租/月费、预估准备完成时间和刷卡机数量必须来自本轮文字或附件中的明确事实；缺失时一次性补问。创建时把客服 ID 写入刷卡机“关联客服工单”，回读后再把刷卡机 ID 写回客服“关联刷卡机”。
- 风控处理复用客服名称、描述、CRM 和语义匹配的一般附件，并只从原文提取订单号、金额、来源、原因、MW 证据和负责人；一般附件与 MW 通知截图分别归档。Chargeback 必填缺失时补问，不用占位值。创建后仍执行风控首节点就绪检查。

以上跨类型可选共享字段统一执行“有值才复制”：来源为空、目标字段停用或类型/枚举不兼容时跳过且不阻塞创建；目标项有更明确的员工输入时禁止覆盖。
- T4 商务、内部跟进和客户情绪/公关当前不自动跨类型创建。内容维护、需求池、客户刷卡机和风控处理不通知 Yoko。

### 内容维护

每次新建内容维护工单时，优先使用常驻 bridge 根据 `CONTENT_PRODUCER_SOURCE_CHAT_ID` 直接读取并注入的“可信内容维护制作人来源”，只解析 `制作：` 到 `确认：` 或群名结尾之间的姓名。bridge 按群名中的姓名顺序持久化轮班，一张工单只分配一位制作人；名单末尾后回到第一位，同一草稿补充消息保持首次分配，名单内容或顺序变化后从新名单第一位开始。`selection_mode=round_robin_single` 时只能解析 producer_names 中的唯一姓名并写入“制作人&交付人”，不得加入 producer_roster 中其他人或改用提交人/登录人。可信 producer_names 已存在时不得再次向员工索取制作人；只有可信数据缺失或读取失败时才回退读取一次。刷新 `meta-roles` 后须把唯一匹配的单个 Meegle userkey 写入角色。缺少环境变量、制作段、唯一人员匹配或唯一角色时，停止自动创建并只询问该项。

## 附件、模板与结果

群聊首条描述和后续媒体按 Skill 的 `ticket_key`、回复关系和同发送者 30 分钟窗口绑定，禁止串单。自动提交授权包含预览中已绑定附件对目标类型附件字段的追加归档；保留旧附件、按资源标识去重并回读。多个附件字段按语义精确匹配，无法唯一匹配时询问；目标类型没有附件字段时明确说明，不能改发评论、借用其他类型字段或跨工单归档。用户用于解释配置或流程的截图不当作业务证据附件。

后续新工作项使用提交时最新已发布流程版本。创建前刷新模板与字段，创建后回读 `template_version`；不固定历史版本，也不因此升级历史工作项。名称只写问题/需求/服务事项本身，不自动拼接店铺、终端或测试前缀。创建或更新成功后必须返回可点击详情链接。

## Yoko 交接边界

只有阻断性问题在创建、回读及附件归档尝试完成后，且真实 `type_key` 位于 `runtime.json` 的 `handoff.enabled_work_item_types` 中，才自动发到 `YOKO_HANDOFF_CHAT_ID` 指定的群并真实 @ Yoko CLI 请求拆解。变量为空时只跳过通知并报告，不影响工单创建。客服联动 bundle 只通知其中新创建的阻断项，并同时返回客服与所有配套项链接；内容维护、需求池、客户刷卡机、风控处理和普通客服工单不通知 Yoko。

飞书 `open_id` 具有应用作用域。必须用当前发送应用从目标群机器人列表唯一解析 Yoko CLI 的 `member_id`，并绑定当前 appId；权限不足、目标不唯一或跨应用 ID 失效时停止通知并报告，禁止使用旧 ID 或普通文本假装 @。发送失败只补发通知、不重建工单；发送成功不代表对方已接手。
