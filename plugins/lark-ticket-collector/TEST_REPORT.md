## 全类型在线元数据验证

- 已通过 `project search` 与 `meta-types` 唯一确认 Pisell项目管理空间 `v2qint`，并枚举平台当前返回的全部 22 个类型。

## 测试发现并已固化

- 需求池提供常规评估、付费开发评估和综合设计三种模板；语义不明确时必须询问，禁止默认第一项。
- 客服工单的 `meta-create-fields` 未返回“下次跟进时间” `field_234f83`，2026-09-28 的内部跟进测试分支曾由创建接口以 `ErrFieldRequired` 拒绝缺失请求。2026-10-03 的当前表单条件截图进一步确认：该字段只在“对应问题类型＝内部跟进处理”时出现并必填，不能外推为所有客服工单的全局必填。插件已改为条件校验；其他客服类型不再补问或写入。
- 风控 Chargeback 的 `meta-create-fields` 未返回必填角色“当前处理的负责人”；首次请求被 `ErrFieldRequired` 拒绝且没有生成工作项。插件已记录角色 key，但仍要求用户明确指定负责人。
- 创建成功后，风控首节点“问题分析”通过 `workflow list-state-required --mode unfinished` 返回 6 个必填业务字段。插件现强制区分创建字段已验证与节点流程就绪；这些字段没有事实依据时不自动补值。
- 飞书内部员工群不会自动映射为客服来源“飞书商家群”；客服问题类型和商家提出人无业务默认值。2026-10-03 用户新增授权：客服星级未明确时默认三星，明确星级覆盖默认；跟进时间仍仅在内部跟进分支适用且无默认值。
- 2026-10-03 的阻断性问题表单条件截图确认：“内部发现人”只在反馈类型为“内部发现”时出现。企业微信/企微群及其他明确商家渠道必须映射为“商家反馈”，不得索取或写入提交员工姓名/邮箱；只有明确内部发现且无法自动解析人员时才补问。
- 2026-10-03 的真实飞书回归暴露：员工只说“创建工单”并附企微商家截图时，异常语义曾抢先路由为独立阻断性问题。现已补充来源优先级：泛化创建请求遇到明确商家来源时先建客服主单，卡慢/报错等异常只用于选择客服 T1/T2 并联动阻断项；商家反馈分支不得索取内部发现人。桥接提示词与机器配置均有契约测试覆盖。
- 只有阻断性问题进入 Yoko CLI 根因拆解交接；需求池和客服工单不会复用 T-BUG、Lv 或 `task拆解指派` 规则。
- 2026-10-02 已在线核对客服工单与内容维护、需求池、风控处理的双向关联字段，以及三类目标的模板、创建字段和角色。配置现支持 T3→内容维护、T5→需求池、风控处理→风控工单的独立查重、创建/复用、双向关联和部分失败恢复；三类业务目标均不通知 Yoko。T3 的客服 4/3/2/1 星映射内容 Q0/Q1/Q2/Q3，“是否需要确认人确认”仍要求真实输入。
- 2026-10-03 已在线核对客户刷卡机类型 `684b899ff9f859147aeca7dd`、默认模板 `3113731`、客服侧“关联刷卡机” `field_baa8cb`、刷卡机侧“关联客服工单” `field_928eb4` 及 6 个创建必填字段。点数、月租/月费、预计完成时间和数量没有默认值。
- 2026-10-03 用户进一步要求所有绿色客服类型使用相同严格配套门禁：T1/T2、T3、T5、客户刷卡机和风控处理任一命中目标未就绪时，客服及其他目标都不开始写入；全部草稿和查重结果就绪后才顺序创建。外部 API 仍不具备跨工作项事务，门禁通过后的部分失败会保存实际 ID 并只续跑缺失步骤，不能把单独客服工单报告为完整完成。
- 阻断性问题真实业务单 [#7126701712](https://project.feishu.cn/67c68170af5c921068953f8b/67df88cf656f61b9b41455d3/detail/7126701712) 已按用户输入创建并回读，流程版本 `166`、节点 `task拆解指派`。用户提供的是配置说明截图而非该支付问题的业务证据，因此未错误归档为附件。

## 尚未完成的生产交接项

飞书消息发送与真实 mention 已在私有测试群用临时人类接收人 Echo 验证。Yoko CLI 尚未加入可由当前发送应用读取的共同群，因此它的当前应用 `member_id`、机器人到机器人通知及实际接手行为尚未验证。生产配置继续保留空 `recipient_member_id`。其余标准类型和模板尚未逐一完成流程就绪级端到端测试，因此当前版本不会把元数据覆盖宣称为生产就绪。
